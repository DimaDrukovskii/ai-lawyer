# Архитектура

## От урока к сервису

Исходная методика (урок «AI-юрист за 40 минут») строилась внутри Claude Code: агент сам собирает
контекст, запускает 12 параллельных исследователей, проверяет их и пишет скилл. Чтобы продавать это
как сервис, оркестрацию пришлось вынести из среды в код. Соответствие:

| Приём из урока | Где в репозитории |
|---|---|
| Нулевой пункт: агент сам берёт контекст и задаёт вопросы | `review/intake.py`, `review/docs_io.py` |
| 12 агентов параллельно, только первоисточники | `research/zones.yaml`, `research/researcher.py`, `tools/domains.py` |
| Состязательная проверка «исходно не верю» | `research/verifier.py`, `prompts/verifier.md` |
| Критики полноты: календарь, форензик, проектировщик проверок | `research/critics.py`, `prompts/critic_*.md` |
| Дозакрытие пробелов отдельными агентами | `research/orchestrator.py` (`_gap_to_zone`) |
| Скилл, который проверяет документы бухгалтера | `skills/usn-marketplace-review/`, `review/` |
| Цена ошибки в деньгах и сроках | `Finding.price_of_error`, зона `penalties-limitation-self-correction` |
| Вердикты: подтверждено / неверно / устарело / преувеличено / непроверяемо | `schemas.Verdict` |
| Три вида утверждений: норма / условная норма / вывод агента | `schemas.ClaimKind` |

## Слои и зависимости

```
cli.py / api.py                      ← тонкие обёртки (можно добавить бота, веб, очередь)
   │
   ├── research/  ─────────────┐
   └── review/    ─────────────┤     оба контура используют:
                                ▼
                   agent.py ← tools/ (search, fetch, белый список)
                      │
                   llm/base.LLMProvider  ← yandex | gigachat | mock
```

Ядро знает только интерфейс `LLMProvider` (`llm/base.py`) и сообщения в формате OpenAI chat.
Смена провайдера — строка `LLM_PROVIDER` в `.env`. Все зависимости передаются явно через `Deps`,
глобального состояния нет.

## Контур 1: исследование (`research/`)

1. **Разведка.** По одному исследователю на зону из `zones.yaml`, параллельно (лимит `MAX_PARALLEL`).
   Исследователь ходит в `web_search` и `fetch_url`, читает тексты норм и возвращает JSON
   (`ZoneFinding`): утверждения, каждое с URL, датой документа и цитатой.
2. **Верификация.** На каждую зону второй, более сильный агент открывает каждую ссылку сам и выносит
   вердикт по каждому утверждению. Утверждение без вердикта считается непроверяемым.
3. **Критики полноты.** Три оптики поверх всей картины ищут пропущенные обязательства, неверно
   проведённые денежные потоки и недостающие сверки.
4. **Дозакрытие.** Критические и высокие пробелы уходят обратно в research отдельными агентами.
5. **База знаний.** `knowledge/<run_id>/` (markdown для людей, `claims.json` для машины).

Каждый этап кэшируется в `out/research/<run_id>/`: упавший прогон продолжается с `--resume`. Падение
одной зоны не роняет прогон (`ZONE_ERRORS`), но фиксируется в `gaps.json`.

### Правило доверия (`research/knowledge.py::classify_claim`)

| Условие | Статус |
|---|---|
| вердикт `confirmed` и есть источник уровня primary / official_text / marketplace | `trusted` |
| вердикт `confirmed`, но источники только «блог» или без источников | `unverified` |
| `kind = opinion` (вывод самого агента) | `unverified` всегда |
| вердикт `wrong` / `outdated` / `exaggerated` | `rejected` |
| вердикт `unverifiable` или нет вердикта | `unverified` |

Уровень источника (`Tier`) считается из домена в `tools/domains.py`, а не берётся из ответа модели:
исследователь не может «назначить» блог первоисточником.

## Контур 2: проверка (`review/`)

1. **Интейк.** Модель задаёт не больше 5 вопросов, без ответа на которые вывод будет неверным. В CLI
   ответы пишутся в `context.local.md` (в git не попадает); в API без интерактива вопросы уходят в отчёт.
2. **Извлечение.** LLM переписывает числа из документов в `ExtractedDocs`. Оценок не даёт.
3. **Детерминированные проверки** (`checks.py`, чистые функции): арифметика налога по периодам,
   сверка КУДиР с декларацией, предел вычета взносов, минимальный налог, срок подачи с переносом на
   рабочий день, ставка. Числа берут из `rules/usn.yaml`; нет значения → «нужен research».
4. **Судья.** Проходит чек-лист по тому, что код не покрывает (признание доходов, расходы, НДС),
   строго по доверенным утверждениям базы знаний. Находка о праве без ссылки на существующий
   `claim_id` помечается `[НЕ ПОДТВЕРЖДЕНО БАЗОЙ]` и `needs_human` (`judge.sanitize`).
5. **Отчёт.** Таблицу находок собирает код; модель пишет только резюме, вопросы бухгалтеру и шаги.

## Что нужно, чтобы продавать как сервис

Код ядра от среды не зависит. Нужно добавить вокруг него (подробнее в `ROADMAP.md`):

- **152-ФЗ.** В документах персональные данные. Для обработки ПДн граждан РФ закон требует
  локализации баз данных в РФ: выбор российской LLM и размещения решает это только частично.
  Согласуй с юристом: оператор ПДн, уведомление Роскомнадзора, договор с провайдером LLM, политика.
  До этого: реальные документы в git не коммитим (`.gitignore`), в логи не пишем.
- **Обезличивание перед LLM:** ИНН, ФИО, номера счетов не нужны модели для проверки арифметики.
- **Очередь задач и хранилище** вместо синхронного `POST /v1/reviews` в `api.py`.
- **Авторизация, лимиты, биллинг, аудит-лог** (кто, когда, какие документы загрузил).
- **Канал доставки:** веб-кабинет или Telegram-бот поверх `run_review`.
- **Человек в контуре:** находки уровня `critical` и все `needs_human` перед выдачей клиенту
  стоит показывать живому специалисту, пока нет данных о точности.

## Известные риски

- **Tool calling у российских моделей.** Если выбранная модель не вызывает инструменты, исследователи
  не смогут читать первоисточники. Проверяется `lawyer doctor` до дорогого прогона.
- **Качество JSON.** Ответ разбирается устойчиво (`jsonutil.extract_json`) с одним проходом ремонта
  (`structured.parse_structured`); упавшая зона не роняет прогон.
- **Поиск.** Yandex Search API отдаёт результаты в base64-XML; парсер защищён от XML-бомб
  (`defusedxml`). Формат сверен с документацией, но не с живым ответом.
- **Устаревание.** Право меняется. `knowledge/<run>/` датируется, `ResearchContext.tax_year` и
  `as_of` попадают во все промпты; пересборку базы нужно планировать регулярно.
